# Running this on your own servers

The numbers in this folder come from a sandbox: SQL Server 2022 and Oracle 26ai Free in Docker on the **same 4-core machine** as R, so there's no network in between. On your servers the absolute times will be higher (network, shared load), and the ratios may shift. The scripts are written to be run there unchanged.

## 1. Packages

R ≥ 4.1 (native pipe, `\(x)`). From the Artifactory CRAN mirror:

```r
install.packages(c("dplyr", "dbplyr", "DBI", "odbc", "duckdb", "callr", "bench", "lobstr", "fs", "purrr", "tidyr",
                   "readr", "lubridate", "arrow", "nanoparquet", "qs2", "data.table", "ggplot2"))
# optional, Oracle without ODBC (needs Oracle Instant Client + its SDK headers):
# install.packages("ROracle")
```

## 2. Connections: ~/.Renviron, never git

```sh
BENCH_MSSQL="Driver={ODBC Driver 18 for SQL Server};Server=myhost,1433;Database=mydb;Trusted_Connection=yes;Encrypt=yes"
BENCH_ORACLE="Driver={Oracle 21 ODBC driver};DBQ=myhost:1521/myservice;UID=me;PWD=..."   # or DSN=...
BENCH_RORACLE="username=me;password=...;dbname=myhost:1521/myservice"                    # only if ROracle is installed
NLS_LANG=AMERICAN_AMERICA.AL32UTF8      # Oracle: without it, accents are lost (see 07)
BENCH_DIR=/home/jovyan/bench-data       # the duckdb file (the in-process engine's copy of the tables)
BENCH_IO_DIR=/tmp/bench-io              # where part 05 writes its files: the disk you want to test
BENCH_ENGINES=mssql,oracle,duckdb       # optional: run only these
BENCH_MAX_ROWS=1e7                      # optional: skip the 100M-row tables (~5 GB less per server)
```

- An engine whose variable is unset is skipped. `duckdb` always runs: it's the in-process floor (no driver, no network).
- Check the driver name with `odbc::odbcListDrivers()`.

## 3. Space and privileges

- `00-setup-tables.R` creates ~60 tables named `bm_*` **on the server** (generated by SQL, nothing is uploaded). Needs CREATE TABLE in a schema you own: about **12 GB per server** including the 1e8-row tables. 03 drops the 1e8-row tables when it's done.
- Synthetic data only: no person-level data, so the `results/` CSVs are safe to commit to GitLab.
- These are big full-table reads. Run them off-peak and tell your DBA. Shared-server load is the biggest source of noise anyway (see [00-method.md](00-method.md)).
- Why not GTTs / `#temp` tables: [06-temp-tables.md](06-temp-tables.md). In short, every case runs in a fresh R process, and a fresh process is a new session that can't see your session's temp data.
- Clean up: `Rscript 99-drop-tables.R` (uses `DROP ... PURGE` on Oracle, so the space is really freed).

## 4. Run

```sh
cd speed-collect-io
Rscript 00-setup-tables.R      # once; re-runs skip tables that already exist
./run-all.sh                   # 00..07 + build-report.R; logs in logs/
# or one part at a time, e.g.
Rscript 03-collect-types-rows-cols.R && Rscript build-report.R
```

- It took ~3 hours here with 4 engines. 03 (the type × rows × columns grid) is the longest.
- Part 05 (files) doesn't touch the servers. Run it once per disk you care about: `BENCH_IO_DIR=/tmp/x Rscript 05-io-formats.R`, then again with `BENCH_IO_DIR` on the filers and on your home volume. Leave `BENCH_DIR` alone: 05 reads its data from the duckdb file there. Each run overwrites `results/05-io.csv`, so copy it away in between.
- In k8s, R sees the node's cores, not your pod's CPU limit. If your pod has a 4-CPU limit, the `qs2 (4 threads)` case is fair. Arrow and data.table default to all the cores they can see.
